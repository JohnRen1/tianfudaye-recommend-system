## 第一类：类型与数据模型（纯 mock 层，低风险）

### 修复 1 — `leadStatus` 枚举补全 + users 类型化

**问题**
`mock-data.ts:2` 的 `LeadStatus` 不含 `'未生成'`，但 `users[5].leadStatus='未生成'`（`mock-data.ts:40`）。现在不报错是因为 `users` 数组没类型标注，纯属侥幸；一旦类型化就会编译失败。且 `statusTheme('未生成')`（`ui.ts:10`）落到 default 返回 `'primary'`（蓝色），语义错误——"未生成"应是中性灰。

**改法**
```ts
// mock-data.ts:2 — 补 '未生成'
export type LeadStatus = '未生成' | '新线索' | '待跟进' | '已分配' | '跟进中' | '已预约' | '已成交' | '无效线索';

// 新增 User 类型并标注 users 数组，让 leadStatus 受约束
export interface User {
  id: number;
  name: string;
  phone: string;
  openid: string;
  identity: string;
  company: string;
  industry: string;
  size: string;
  sourceActivity: string;
  sourceQr: string;
  tags: string[];
  registeredAt: string;
  activeAt: string;
  leadStatus: LeadStatus;
}
export const users: User[] = [ /* ... */ ];

// ui.ts:13 — 把 '未生成' 归到中性灰，与"无效线索"同档
if (['已下架', '无效线索', '未生成'].includes(status)) return 'default';
```

**影响文件**：`lib/mock-data.ts`、`lib/ui.ts`
**性质**：additive，不破坏其他页面。

### 修复 2 — 用 `userId` 外键替换 `name` 字符串关联（最高优先）

**问题**
详情页全靠姓名匹配或全量渲染：

- `reports.find(r => r.user === user.name)`（`[id]/page.tsx:19`）
- `leads.find(l => l.name === user.name)`（`[id]/page.tsx:20`）
- `qaRecords.map(...)` 全量渲染所有人的问答（`[id]/page.tsx:59`）
- `userTimeline.map(...)` 全局静态，所有用户显示同一条（`[id]/page.tsx:51`）
- `materialItems.slice(0,3)` 取目录前 3 条，根本不是该用户领取的（`[id]/page.tsx:58`）

同名用户会数据污染；`?? reports[0]` / `?? users[0]` 的 fallback 还会把"无数据"伪装成"别人的数据"。

**改法**
```ts
// mock-data.ts — 各实体补 userId 外键
// 现有姓名对应：李明=1 张倩=2 赵瑞=3 王磊=4 陈晨=5
reports:      每条 + userId
leads:        每条 + userId
qaRecords:    每条 + userId
userTimeline: 每条 + userId

// materialItems 是"资料目录"，不该当领取记录用 —— 新增 join 表：
export const materialClaims = [
  { userId: 1, materialId: 'MAT-001', claimedAt: '2026-06-04 10:31' },
  // ...
];

// [id]/page.tsx — find 改 filter，去掉 ?? fallback，加空态
const userReport = reports.find(r => r.userId === user.id);        // 可能 undefined
const userLeads  = leads.filter(l => l.userId === user.id);
const userQa     = qaRecords.filter(q => q.userId === user.id);
const userTl     = userTimeline.filter(t => t.userId === user.id);
// 各处渲染前判空：userReport ? <...> : <空态提示>
```

**影响文件**：`lib/mock-data.ts`（additive 加字段）、`app/users/[id]/page.tsx`
**注意**：`userReport` 用在顾问摘要卡（`[id]/page.tsx:44-45`）和 report tab（`:60`），需统一处理 undefined。

### 修复 3 — `sourceActivity` / `sourceQr` 改为 id 关联

**问题**
`user.sourceActivity` 存活动名称字符串、`user.sourceQr` 存的值（`'ACT-20260702-001'`、`'CONSULTANT-ZHOU'`、`'CHANNEL-SZ-002'`）既不等于 `qrCodeItems.id`（如 `QR-ACT-001`）也不等于 `inviteCode`（如 `ACT20260702`），三套命名互不对齐（`mock-data.ts:36-40` vs `:72-76`）。活动改名即数据断裂。

**改法**
- User 增 `sourceActivityId`（→`activities.id`）、`sourceQrId`（→`qrCodeItems.id`）
- 展示时 join 名称
- 同时校正 5 条用户的 sourceQr 值到真实存在的 `qrCodeItems.id`

**影响文件**：`lib/mock-data.ts`、`app/users/page.tsx`（第 75-76 列展示改 join）、`app/users/[id]/page.tsx:36,57`
**时机**：可现在做，但需配合后续 DB 外键设计，建议和 API 契约阶段一起定。

## 第二类：页面交互（纯前端可做，部分会引入"假写状态"）

### 修复 4 — 用户列表筛选逻辑

**问题**
`users/page.tsx:45-55` 的 Input/Select/DateRangePicker 全是无 `onChange` 的受控空壳，查询/重置按钮无事件，`pagination.total: users.length`（`:100`）写死。

**改法**
- 加受控 state（phone/name/activity/identity/tag/dateRange）
- `useMemo` 计算 `filtered`
- `Table data={filtered}`、`total={filtered.length}`
- 重置清空 state
- 纯前端 mock 过滤，后续整体替换为 `GET /api/users?...` query

**影响文件**：`app/users/page.tsx` 单文件，本地修改。

---

### 修复 5 — 行操作 / 批量 / 导出占位

**问题**
编辑标签、生成线索（`page.tsx:95` moreItems 但 `TableRowActions` 没接 `onMoreClick`）、批量打标签、导出（`:62` 按钮无 onClick）全部点击无响应。

**改法分级**
- **导出 CSV**：纯前端可实现（filtered 数据 → Blob 下载），建议现在做。
- **编辑标签 / 生成线索 / 批量打标签**：是写操作，mock 阶段实现需把 `users` 从 import 常量改成 `useState` 副本来维护假状态。**建议这几项等接 API 再做**——否则会造出"刷新即丢失"的假数据，反而误导验收。

**影响文件**：`app/users/page.tsx`、`components/table-row-actions.tsx`

## 第三类：认证与会话（建议随 Supabase 阶段做）

### 修复 7 — 落地页会话持久化 + 企业信息补录

**问题**
`login-register-form.tsx:58,68` 登录成功只调 `onSuccess?.()`，无 token、无 context、无存储，刷新即丢登录态；且表单只有 phone+code，缺 `company/industry/size/identity`，而 `userTimeline:45` 写的是"手机号授权登录**并补充企业信息**"。

**目标方案**
- 真实：Supabase Auth `signInWithOtp({phone})` / 微信 OAuth，session 存 cookie
- `/api/auth/send-code` 发真实验证码
- 登录后增加"补充企业信息"步骤（分两步：先手机号登录，再补企业信息），对应 User 表这些字段设为 nullable

**影响文件**：`components/mobile/login-register-form.tsx`、新增 auth API、新增企业信息补录步骤组件

---

### 修复 8 — 管理后台认证与角色

**问题**
- `login/page.tsx:17-19` 硬编码 `admin/admin123`，写死 `'mock-admin-token'`
- `admin-shell.tsx:63-64` 只判断 token key 是否存在——任何人手填 localStorage 即绕过
- `admin-shell.tsx:80` 用 `username==='admin'` 判角色，与 CLAUDE.md 规定的"市场运营/税务顾问/管理者"三角色不符
- `login/page.tsx:55` "记住登录状态"勾选框无任何逻辑

**目标方案**
- `admin_users` 表 + `AdminRole = 'market_ops' | 'tax_advisor' | 'manager'` 类型，Supabase Auth 登录返回 JWT
- `admin-shell` 校验真实 session + role，做路由级权限守卫（替换 `:57-72` 整段）
- "记住登录状态"：勾选→persistent session，不勾→sessionStorage

**影响文件**：`app/login/page.tsx`、`components/admin-shell.tsx`、新增 admin auth API、新增 `admin_users` 数据模型

## 推荐执行顺序

| 批次 | 含修复 | 依赖 | 风险 |
|------|--------|------|------|
| **第一批（可立即做）** | 1 类型、2 userId 关联+空态、6 预约 mock、4 前端筛选、5 仅导出 CSV | 无，纯 mock 层 | 低，additive |
| **第二批（API 契约阶段）** | 3 id 关联、5 写操作（编辑/生成/批量） | 需配合 DB 外键 / 写接口 | 中 |
| **第三批（Supabase 接入）** | 7 落地页会话、8 后台认证与角色 | Supabase Auth | 高，涉及安全 |

第一批让 mock 数据结构提前贴近真实模型，对后续接 API 几乎零返工，且不引入任何"假写状态"误导验收。
