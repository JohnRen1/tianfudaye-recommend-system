## 3. 表结构

### 3.1 public.admin_users

管理后台用户表，存储市场运营、税务顾问、管理者三种角色的账号。

| 列名 | 类型 | 可空 | 默认值 | 约束 | 说明 |
|------|------|------|--------|------|------|
| `id` | `uuid` | NOT NULL | `gen_random_uuid()` | PK | 与 Supabase auth.users.id 对应 |
| `username` | `text` | NOT NULL | — | UNIQUE, CHECK(3-50字符，字母数字下划线) | 登录用户名 |
| `password_hash` | `text` | NOT NULL | — | — | bcrypt hash（$2b$12$...），API 层不暴露此列 |
| `display_name` | `text` | NOT NULL | — | CHECK(trim 后非空) | Shell 顶栏展示名称 |
| `role` | `admin_role_enum` | NOT NULL | — | — | 管理员角色枚举 |
| `is_active` | `boolean` | NOT NULL | `true` | — | false 时拒绝登录（软停用） |
| `last_login_at` | `timestamptz` | NULL | `NULL` | — | 最近成功登录时间，登录接口写入 |
| `created_at` | `timestamptz` | NOT NULL | `now()` | — | 账号创建时间（UTC） |
| `updated_at` | `timestamptz` | NOT NULL | `now()` | — | trigger 自动维护 |

**关键设计决策**：
- `id` 采用 UUID 而非自增序列，与 Supabase Auth 的 `auth.uid()` 直接映射，无需额外关联字段。
- `password_hash` 存在表中作为备用认证路径，主认证流程走 Supabase Auth；bcrypt cost=12 平衡安全性与性能。
- `is_active = false` 触发 `ADMIN_AUTH_ACCOUNT_DISABLED` 错误码（见 API 契约第六节），不物理删除账号以保留审计记录。

### 3.2 public.users

落地页注册的外部端用户表。

| 列名 | 类型 | 可空 | 默认值 | 约束 | 说明 |
|------|------|------|--------|------|------|
| `id` | `uuid` | NOT NULL | `gen_random_uuid()` | PK | 与 Supabase auth.users.id 对应 |
| `phone` | `text` | NOT NULL | — | UNIQUE, CHECK(^1[0-9]{10}$) | 完整 11 位手机号，展示层脱敏 |
| `openid` | `text` | NULL | `NULL` | UNIQUE PARTIAL (WHERE NOT NULL) | 微信 openid，手机号用户未绑定时为 null |
| `name` | `text` | NULL | `NULL` | — | 姓名，注册第二步补填 |
| `identity` | `text` | NULL | `NULL` | — | 用户身份（企业老板/财务负责人/创业者） |
| `company` | `text` | NULL | `NULL` | — | 企业名称，注册第二步补填 |
| `industry` | `text` | NULL | `NULL` | — | 行业，注册第二步补填 |
| `size` | `text` | NULL | `NULL` | — | 企业规模，注册第二步补填 |
| `source_activity_id` | `uuid` | NULL | `NULL` | — | 来源活动 UUID（FK 待补全，见第 9 节） |
| `source_qr_id` | `uuid` | NULL | `NULL` | — | 来源二维码 UUID（FK 待补全，见第 9 节） |
| `tags` | `text[]` | NOT NULL | `'{}'` | CHECK(array_length <= 20) | 用户标签，最多 20 个 |
| `lead_status` | `lead_status_enum` | NOT NULL | `'none'` | — | 线索状态，默认未生成 |
| `is_profile_complete` | `boolean` | NOT NULL | `false` | — | 注册第二步是否完成 |
| `registered_at` | `timestamptz` | NOT NULL | `now()` | — | 注册时间（UTC） |
| `active_at` | `timestamptz` | NOT NULL | `now()` | — | 最近活跃时间，trigger 自动更新 |
| `updated_at` | `timestamptz` | NOT NULL | `now()` | — | trigger 自动维护 |

**关键设计决策**：
- `phone` 存储完整 11 位手机号（审计不确定项 #1 决策：数据库不存脱敏格式，展示层处理）。脱敏逻辑由 API 层实现，`UserListItemDTO.phoneMasked` 在服务端格式化后返回。
- `openid` 使用部分唯一索引（`WHERE openid IS NOT NULL`），允许多行 openid 为 null 而不违反唯一性。
- `name`、`identity`、`company`、`industry`、`size` 均可为 null，支持注册分两步：先手机号验证码登录，后补充企业信息（审计不确定项 #4）。
- `source_activity_id` / `source_qr_id` 存 UUID 外键而非名称字符串（修复审计 S1：`sourceActivity` 改为 `sourceActivityId`），避免活动改名后数据断裂。
- `tags` 使用 `text[]` 而非关联表，满足当前阶段灵活打标需求；GIN 索引支持 `@>` 运算符查询。
- `registered_at` 与 `active_at` 语义分离：前者记录账号首次创建时间（只写），后者追踪用户最近访问行为（持续更新）。

## 4. 索引说明

### 4.1 admin_users 索引

| 索引名 | 列 | 类型 | 用途 |
|--------|-----|------|------|
| `admin_users_pkey` | `id` | B-Tree（PK 隐式） | 主键查找 |
| `admin_users_username_uq` | `username` | B-Tree（UNIQUE 隐式） | 登录时 WHERE username = $1 |
| `idx_admin_users_role` | `role` | B-Tree | 按角色筛选管理员；`get_my_admin_role()` / `is_admin()` 函数的 WHERE 条件 |
| `idx_admin_users_active` | `is_active` | B-Tree（partial，WHERE is_active=true） | 活跃管理员过滤，减少索引体积 |

### 4.2 users 索引

| 索引名 | 列 | 类型 | 用途 |
|--------|-----|------|------|
| `users_pkey` | `id` | B-Tree（PK 隐式） | 主键查找，`GET /api/admin/users/:id` |
| `users_phone_uq` | `phone` | B-Tree（UNIQUE 隐式） | 手机号唯一性校验；`WHERE phone = $1` 精确查找 |
| `idx_users_openid_uq` | `openid` | B-Tree（partial，WHERE NOT NULL） | 微信登录时通过 openid 查找已有用户 |
| `idx_users_name_trgm` | `name` | GIN（pg_trgm） | 姓名模糊搜索（LIKE '%搜索词%'），对应 `UserQueryDTO.name` |
| `idx_users_source_activity_id` | `source_activity_id` | B-Tree（partial，WHERE NOT NULL） | 来源活动筛选（`UserQueryDTO.sourceActivityId`） |
| `idx_users_source_qr_id` | `source_qr_id` | B-Tree（partial，WHERE NOT NULL） | 来源二维码筛选 |
| `idx_users_lead_status` | `lead_status` | B-Tree | 线索状态筛选；统计 `withLead`（`lead_status != 'none'`） |
| `idx_users_registered_at` | `registered_at DESC` | B-Tree | 时间范围筛选；默认排序（`sortBy=registeredAt desc`） |
| `idx_users_active_at` | `active_at DESC` | B-Tree | 按最近活跃时间排序（`sortBy=activeAt`） |
| `idx_users_tags_gin` | `tags` | GIN | `tags @> ARRAY['意向']` 查询；统计 `highIntent` / `highRisk` |

**分页排序稳定性说明**：列表 API 默认按 `registered_at DESC` 排序，同一时间戳内顺序不确定。如需稳定分页，建议在 ORDER BY 末尾追加 `id ASC` 作为 tiebreaker。`idx_users_registered_at` 使用 DESC 顺序与默认排序方向一致，避免隐式倒排。

## 5. RLS 策略

所有表均启用 Row Level Security（`ALTER TABLE ... ENABLE ROW LEVEL SECURITY`）。  
Service Role（后端 API / Server Action 使用）绕过 RLS，无需额外策略。

### 5.1 辅助函数

**`public.get_my_admin_role()`**
- 从 `admin_users` 查当前 `auth.uid()` 的角色。
- `SECURITY DEFINER`：以定义者权限执行，避免 RLS 递归调用。
- `STABLE`：同一事务内结果缓存，减少 RLS 策略中的重复查询开销。
- 返回 `NULL` 时（非管理员 / 账号已停用）视为无权限。

**`public.is_admin()`**
- 判断当前用户是否为任意活跃管理员。
- 同样使用 `SECURITY DEFINER` + `STABLE`。
- 用于 `users` 表的管理员读权限策略。

### 5.2 admin_users 表策略

| 策略名 | 操作 | 条件 | 用途 |
|--------|------|------|------|
| `admin_users_select_self` | SELECT | `auth.uid() = id` | 管理员读取自己的行（Shell 顶栏展示） |
| `admin_users_select_by_manager` | SELECT | `get_my_admin_role() = 'manager'` | manager 查询所有管理员列表 |
| `admin_users_insert_by_manager` | INSERT | `get_my_admin_role() = 'manager'` | manager 创建新管理员账号 |
| `admin_users_update_by_manager` | UPDATE | `get_my_admin_role() = 'manager'` | manager 修改角色、重置密码、停用账号 |
| `admin_users_delete_by_manager` | DELETE | `get_my_admin_role() = 'manager'` | manager 删除管理员（生产建议用软删除代替） |

**password_hash 访问控制**：RLS 策略为行级控制，无法在策略层屏蔽单列。`password_hash` 的访问控制在 API 层实现——所有返回管理员信息的查询（`AdminProfileDTO`）显式指定列，不 SELECT `password_hash`。

### 5.3 users 表策略

| 策略名 | 操作 | 条件 | 用途 |
|--------|------|------|------|
| `users_select_self` | SELECT | `auth.uid() = id` | 端用户读自己（`GET /api/auth/me`） |
| `users_update_self` | UPDATE | `auth.uid() = id` | 端用户更新自己（补录企业信息）；可操作列由 API 层白名单控制 |
| `users_select_by_admin` | SELECT | `is_admin()` | 任意管理员读所有用户（列表 / 详情） |
| `users_update_by_market_ops_or_manager` | UPDATE | `get_my_admin_role() IN ('market_ops','manager')` | 运营/管理者更新用户信息、标签、线索状态 |
| `users_insert_by_market_ops_or_manager` | INSERT | `get_my_admin_role() IN ('market_ops','manager')` | 后台手动创建用户 |

**DELETE 禁止**：`users` 表不设 DELETE 策略，任何角色（包括 manager）均不能通过 RLS 删除用户行。删除操作必须通过 Service Role 执行（需人工确认），并在执行前记录审计日志。

**phoneRaw 列级权限**：`users` 表存完整手机号（`phone` 列）。RLS 控制行访问，列级脱敏在 API 层实现：
- `tax_advisor` / `manager` 调用时，服务端同时返回 `phoneMasked` 和 `phoneRaw`
- `market_ops` 调用时，服务端仅返回 `phoneMasked`，不返回 `phoneRaw`

## 6. Trigger 说明

### 6.1 admin_users_set_updated_at

| 属性 | 值 |
|------|----|
| 触发时机 | BEFORE UPDATE |
| 触发粒度 | FOR EACH ROW |
| 触发函数 | `public.set_updated_at()` |
| 作用 | 将 `updated_at` 更新为 `now()`，无需应用层手动维护 |

### 6.2 users_set_updated_at

| 属性 | 值 |
|------|----|
| 触发时机 | BEFORE UPDATE |
| 触发粒度 | FOR EACH ROW |
| 触发函数 | `public.set_updated_at()` |
| 作用 | 将 `updated_at` 更新为 `now()` |

### 6.3 users_set_active_at

| 属性 | 值 |
|------|----|
| 触发时机 | BEFORE UPDATE |
| 触发粒度 | FOR EACH ROW |
| 触发函数 | `public.set_users_active_at()` |
| 作用 | 任意字段 UPDATE 时将 `active_at` 更新为 `now()`，作为兜底保障 |

**说明**：`active_at` 的更新在 trigger 层是粗粒度的（任意 UPDATE 均触发），更精细的业务场景（如仅在用户登录、发起问答、浏览资料时更新）建议在 API 层显式调用，trigger 作为兜底防止遗漏。

`set_updated_at()` 与 `set_users_active_at()` 的触发顺序：同一 BEFORE UPDATE 事件中，两个 trigger 均更新 `NEW` 中的字段，执行顺序由 PostgreSQL 按触发器名称字母序决定（`users_set_active_at` 先于 `users_set_updated_at`）。两者均作用于 `NEW`，结果幂等。

## 7. Migration 执行顺序

本模块仅包含一个 migration 文件，内部执行顺序如下：

```
1. CREATE EXTENSION (pg_trgm, moddatetime)
2. CREATE TYPE admin_role_enum
3. CREATE TYPE lead_status_enum
4. CREATE FUNCTION get_my_admin_role()
5. CREATE FUNCTION is_admin()
6. CREATE FUNCTION set_updated_at()
7. CREATE TABLE admin_users
8. CREATE TRIGGER admin_users_set_updated_at
9. CREATE TABLE users
10. CREATE FUNCTION set_users_active_at()
11. CREATE TRIGGER users_set_updated_at
12. CREATE TRIGGER users_set_active_at
13. CREATE INDEX（admin_users 相关）
14. CREATE INDEX（users 相关）
15. ALTER TABLE ... ENABLE ROW LEVEL SECURITY
16. CREATE POLICY（admin_users 相关）
17. CREATE POLICY（users 相关）
18. INSERT seed data（仅本地/测试环境）
```

后续模块 migration 需在本 migration 之后执行（因为其他模块表会引用 `users.id` 外键）：

```
20260610120001_create_activities_table.sql
  → 创建 activities 表

20260610120002_create_qr_codes_table.sql
  → 创建 qr_codes 表

20260610130000_add_users_fk_constraints.sql
  → ALTER TABLE public.users
      ADD CONSTRAINT users_source_activity_id_fk
        FOREIGN KEY (source_activity_id) REFERENCES public.activities(id)
        ON DELETE SET NULL;
  → ALTER TABLE public.users
      ADD CONSTRAINT users_source_qr_id_fk
        FOREIGN KEY (source_qr_id) REFERENCES public.qr_codes(id)
        ON DELETE SET NULL;
```

## 8. 回滚方法

### 8.1 回滚 migration 文件

如需撤销本 migration，在 Supabase 本地开发环境中：

```bash
# 方法一：使用 supabase CLI reset（会重置整个数据库到初始状态）
supabase db reset

# 方法二：手动执行 rollback SQL（不影响其他 migration）
# 在 Supabase Studio SQL 编辑器或 psql 中执行以下语句：
```

### 8.2 回滚 SQL（手动执行，顺序不可颠倒）

```sql
-- 步骤 1：删除依赖枚举类型的表（CASCADE 同时删除 trigger、索引、策略）
DROP TABLE IF EXISTS public.users CASCADE;
DROP TABLE IF EXISTS public.admin_users CASCADE;

-- 步骤 2：删除辅助函数
DROP FUNCTION IF EXISTS public.set_users_active_at();
DROP FUNCTION IF EXISTS public.set_updated_at();
DROP FUNCTION IF EXISTS public.is_admin();
DROP FUNCTION IF EXISTS public.get_my_admin_role();

-- 步骤 3：删除枚举类型
DROP TYPE IF EXISTS public.lead_status_enum;
DROP TYPE IF EXISTS public.admin_role_enum;

-- 步骤 4：扩展通常保留（可能被其他对象依赖）
-- 如需清理：
-- DROP EXTENSION IF EXISTS moddatetime;
-- DROP EXTENSION IF EXISTS pg_trgm;
```

### 8.3 注意事项

- 若其他 migration 已添加外键（如 `assessment_reports.user_id → users.id`），必须先回滚那些 migration，再回滚本 migration。
- `DROP TABLE ... CASCADE` 会同时删除所有依赖此表的外键约束，但不会删除引用此表的其他表本身。
- 回滚操作不可逆，执行前务必确认数据库中无业务数据（生产环境禁止执行）。

### 10.1 外键约束补全计划

当前 `users.source_activity_id` 和 `users.source_qr_id` 未添加 FOREIGN KEY constraint，原因是 `activities` 和 `qr_codes` 表在本 migration 中尚未创建。

| 字段 | 目标表 | 删除策略 | 补全时机 |
|------|--------|---------|---------|
| `users.source_activity_id` | `activities.id` | `ON DELETE SET NULL` | 活动管理模块 migration 创建 `activities` 表后，通过新 migration 添加 |
| `users.source_qr_id` | `qr_codes.id` | `ON DELETE SET NULL` | 二维码管理模块 migration 创建 `qr_codes` 表后，通过新 migration 添加 |

删除策略选择 `ON DELETE SET NULL` 的原因：活动或二维码被删除时，历史用户的来源归因数据不应随之丢失，而是将关联 id 置为 null，保留 `sourceActivityName` 等冗余字段的历史记录（由 API 层处理 join 失败的降级展示）。

补全方式（新 migration 示例）：

```sql
-- migration: 20260610130000_add_users_fk_constraints.sql
ALTER TABLE public.users
  ADD CONSTRAINT users_source_activity_id_fk
    FOREIGN KEY (source_activity_id)
    REFERENCES public.activities(id)
    ON DELETE SET NULL
    DEFERRABLE INITIALLY DEFERRED;

ALTER TABLE public.users
  ADD CONSTRAINT users_source_qr_id_fk
    FOREIGN KEY (source_qr_id)
    REFERENCES public.qr_codes(id)
    ON DELETE SET NULL
    DEFERRABLE INITIALLY DEFERRED;
```
