## 二、设计原则与审计总纲对应

| 审计问题 | 对应决策 | 契约体现位置 |
|----------|----------|-------------|
| **S1** — advisor/activity 字符串关联 | `advisorId` / `activityId` 改外键，展示名称服务端 join 返回 | `QrCodeListItemDTO`、`QrCodeCreateDTO` |
| **S2** — 扫码归因链四套标识不对齐 | 统一以 `qrCodeId`（qr_codes.id）为唯一外键；定义 URL 参数三协议；定义扫码上报 DTO | `TrackingUrlParams`、`QrScanTrackRequestDTO`、`QrCodeListItemDTO.id` |
| **S2** — validPeriod 非结构化字符串 | 拆分为 `validFrom` / `validTo`（ISO 8601，null = 长期有效） | `QrCodeListItemDTO`、`QrCodeCreateDTO` |
| **S2** — 落地页无 URL 参数读取逻辑 | 定义 `TrackingUrlParams` 协议；落地页 `app/page.tsx` 需读取并传入组件 | `tracking.ts`、`TrackingContext` |
| **S4** — 两端字段命名不一致（teacher/place vs speaker/location） | `TrackingActivityDTO` 统一按落地页命名，服务端做字段映射 | `TrackingActivityDTO` |
| **S6** — 统计值混在列表 DTO | 全局聚合统计归入 `QrCodeStatisticsDTO`（独立接口）；单条计数器保留在列表 DTO | `QrCodeStatisticsDTO` |

## 三、二维码标识统一方案（S2 核心）

### 3.1 问题：四套标识并存

| 标识 | 出处 | 示例值 | 问题 |
|------|------|--------|------|
| `qrCodeItems.id` | mock-data.ts:72 | `QR-ACT-001` | 系统主键，但格式不规范（应为 UUID） |
| `qrCodeItems.inviteCode` | mock-data.ts:72 | `ACT20260702` | 可读短码，全局唯一 |
| `user.sourceQr` | mock-data.ts:36 | `ACT-20260702-001`（不是上面任何一个） | 混用，与两者均不对齐 |
| `{activity.id}-INVITE` 拼接 | activities/page.tsx:152 | `A003-INVITE` | 独立体系，与 qrCodeItems 无关联 |

### 3.2 解决方案：以 qrCodeId 为唯一外键

```
数据库主键：qr_codes.id（UUID）
↓ 扫码链接：?qr_id={qr_codes.id}
↓ 落地页入口：读取 qr_id，调用 POST /api/track/qr-scan
↓ 注册接口：携带 sourceQrId（即 qr_codes.id）
↓ 用户表：users.source_qr_id = qr_codes.id（外键）
↓ 线索表：leads.source_qr_id = qr_codes.id（外键）
```

### 3.3 URL 参数协议

**完整格式**：
```
https://m.example.com/?qr_id=<uuid>&activity_id=<activityId>&invite=<inviteCode>
```

| 参数 | 取值来源 | 必填 | 说明 |
|------|----------|------|------|
| `qr_id` | `qr_codes.id`（UUID，系统主键） | 是（扫码场景） | 唯一归因外键，后端以此查询；不可用 inviteCode 替代 |
| `activity_id` | `activities.id` | 否 | 二维码绑定了活动时携带；落地页据此动态渲染活动内容；未绑定时省略 |
| `invite` | `qr_codes.inviteCode`（可读短码） | 否 | 仅用于页面展示，不做业务逻辑判断 |

**废弃的拼接格式**（迁移后不再使用）：
- `{activity.id}-INVITE`（如 `A003-INVITE`）— 活动管理页硬编码生成，已废弃
- `user.sourceQr` 直接存短码字符串 — 改为 `source_qr_id` 外键

## 五、DTO 详情

### 5.1 QrCodeListItemDTO

用于二维码列表表格每行数据。

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `id` | `string` | 是 | UUID 主键，S2 归因外键（qrCodeId） |
| `name` | `string` | 是 | 二维码名称 |
| `type` | `QrType` | 是 | 类型枚举（英文值） |
| `inviteCode` | `string` | 是 | 可读短码，系统生成，唯一，URL invite 参数来源 |
| `activityId` | `string \| null` | 是 | 绑定活动外键 id（S1） |
| `activityName` | `string \| null` | 是 | 绑定活动名称，服务端 join，前端只读 |
| `advisorId` | `string \| null` | 是 | 绑定顾问外键 id（S1），null = 未绑定 |
| `advisorName` | `string \| null` | 是 | 绑定顾问名称，服务端 join，前端只读 |
| `channel` | `string` | 是 | 渠道标识 |
| `validFrom` | `string \| null` | 是 | 有效期起始，ISO 8601，null = 无起始限制 |
| `validTo` | `string \| null` | 是 | 有效期截止，ISO 8601，null = 长期有效 |
| `status` | `QrStatus` | 是 | 状态枚举 |
| `scans` | `number` | 是 | 单条累计扫码次数 |
| `registers` | `number` | 是 | 单条扫码后注册用户数 |
| `leads` | `number` | 是 | 单条归因线索数 |
| `createdAt` | `string` | 是 | 创建时间，ISO 8601 |
| `updatedAt` | `string` | 是 | 最近更新时间，ISO 8601 |

### 5.2 QrCodeDetailDTO

继承 `QrCodeListItemDTO` 全部字段，额外增加：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `trackingUrl` | `string` | 是 | 完整追踪链接，服务端按协议拼接后返回，前端直接展示/复制 |
| `qrImageUrl` | `string \| null` | 是 | 二维码图片 URL，null 表示尚未生成 |

**trackingUrl 拼接规则**（服务端负责）：
```
有绑定活动：https://{domain}/?qr_id={id}&activity_id={activityId}&invite={inviteCode}
无绑定活动：https://{domain}/?qr_id={id}&invite={inviteCode}
```

### 5.3 QrCodeCreateDTO

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `name` | `string` | 是 | 二维码名称 |
| `type` | `QrType` | 是 | 类型；"新建邀请码"快捷入口固定传 `'advisor'` |
| `activityId` | `string` | 否 | 绑定活动外键 id |
| `advisorId` | `string` | 否 | 绑定顾问外键 id |
| `channel` | `string` | 是 | 渠道标识 |
| `validFrom` | `string` | 否 | 有效期起始，ISO 8601；不传 = 无起始限制 |
| `validTo` | `string` | 否 | 有效期截止，ISO 8601；不传 = 长期有效 |
| `status` | `QrStatus` | 否 | 初始状态，默认 `'active'` |

**服务端生成字段（不接受客户端提交）**：`id`、`inviteCode`、`trackingUrl`、`qrImageUrl`、`scans`、`registers`、`leads`、`createdAt`、`updatedAt`。

### 5.4 QrCodeUpdateDTO

所有字段可选，PATCH 语义（只更新传入字段）。

| 字段 | 类型 | 说明 |

### 二维码管理错误码（admin-system）

| 错误码 | HTTP 状态 | 说明 |
|--------|----------|------|
| `QR_NOT_FOUND` | 404 | 二维码不存在 |

| `QR_ACTIVITY_NOT_FOUND` | 400 | 绑定的 activityId 不存在 |
| `QR_ADVISOR_NOT_FOUND` | 400 | 绑定的 advisorId 不存在 |
| `QR_VALID_PERIOD_INVALID` | 400 | validTo 早于 validFrom |
| `QR_BULK_IDS_EMPTY` | 400 | 批量操作 ids 为空数组 |
| `QR_BULK_IDS_TOO_MANY` | 400 | 批量操作 ids 超出上限（100） |
| `QR_PERMISSION_DENIED` | 403 | 权限不足（如 tax_advisor 尝试创建二维码） |

## 八、认证与权限

### 8.1 认证方案

二维码管理接口与用户管理一致，使用管理员 Bearer token：

```
Authorization: Bearer <adminJwt>
```

落地页归因接口（`/api/track/qr-scan`、`/api/activities/:id/landing`）为公开接口，无需认证。

### 8.2 管理员角色权限矩阵

|------|-----------|-------------|---------|
| 查看二维码列表/详情/统计 | 是 | 是 | 是 |
| 获取筛选选项 | 是 | 是 | 是 |
| 新建二维码 | 是 | 否 | 是 |

## 十、关键字段约定

### 10.1 validFrom / validTo 与"长期有效"

| 场景 | validFrom | validTo | 前端展示 |
|------|-----------|---------|---------|
| 固定有效期 | `"2026-06-01T00:00:00+08:00"` | `"2026-07-02T23:59:59+08:00"` | `"2026-06-01 至 2026-07-02"` |
| 长期有效 | `null` 或有起始 | `null` | `"长期有效"` |
| 有起始无截止 | `"2026-06-01T00:00:00+08:00"` | `null` | `"2026-06-01 起长期有效"` |

前端判断：`validTo === null` 时展示"长期有效"，DateRangePicker 回填时将 null 映射为空值。

对应审计不确定项 #4 决策：使用 `validTo = null` 表示长期有效，不引入 `isPermanent` 布尔字段。

### 10.2 inviteCode 与 id 的语义区别

| 字段 | 用途 | 特性 |
|------|------|------|
| `id`（UUID） | 系统内部主键，归因外键，URL `qr_id` 参数来源 | 全局唯一，不可变 |
| `inviteCode` | 对外可读短码，URL `invite` 参数来源，展示用 | 全局唯一，系统生成，用户不可写 |

对应审计不确定项 #1 决策：两者均存储，`id` 为系统查询键，`inviteCode` 为人类可读标识；`inviteCode` 建唯一索引以支持历史数据查询，但新建系统一律以 `id` 做外键关联。

### 10.3 scans / registers / leads 的存储策略

对应审计不确定项 #2 决策：采用**预存计数器**方案。

- 三个字段存储在 `qr_codes` 表中，事件发生时原子递增（PostgreSQL `UPDATE ... SET scans = scans + 1`）
- 注册触发 `registers+1`，线索生成触发 `leads+1`，均在对应接口的事务中完成
- 定期对账任务校验计数器与实际聚合值是否一致

### 10.4 "新建邀请码"与"新建二维码"的关系

对应审计不确定项 #3 决策：**同一实体，共用 `POST /api/admin/qr-codes` 接口**。

"新建邀请码"快捷入口是 type 固定为 `'advisor'` 的语法糖，后端无需单独接口，前端在提交时自动附加 `type: 'advisor'`。

### 10.5 channel 字段的来源

对应审计不确定项 #6 决策：当前阶段 `channel` 值来自后端维护的字典表，通过 `GET /api/admin/qr-codes/filter-options` 中的 `channels` 数组返回给前端，不在前端硬编码。未来可做渠道字典管理后台。

## 十三、遗留不确定项（需产品确认）

| # | 问题 | 当前契约假设 | 需要决策的内容 |
|---|------|------------|--------------|
| 1 | `channel` 字段是否需要独立的渠道字典管理后台 | 当前阶段通过 filter-options 接口动态返回，值为后端维护的枚举列表 | 产品确认：是否需要运营人员自行新增/删除渠道 |
| 2 | 同一活动是否可以关联多个二维码，还是一对一 | 一对多（一个活动可有多个二维码，每个二维码最多绑定一个活动） | 产品确认：是否限制活动-二维码绑定数量 |
| 3 | `inviteCode` 的生成规则是什么（全随机 or 有规律的可读短码） | 服务端生成，格式由后端决定，前端不感知生成规则 | 后端决定格式，运营是否需要自定义 inviteCode |
| 4 | 扫码事件是否需要去重（同一用户 / 设备短时间内多次扫码是否都计入 scans） | 不去重，每次扫码均计入（简单实现） | 产品确认是否需要去重窗口（如 1 小时内同 IP 不重复计数） |
| 5 | `QrScanEventLogDTO` 是否需要对运营开放查询（二维码扫码明细列表） | 当前契约中作为内部日志，不暴露前台查询接口 | 产品确认是否需要在管理后台展示每条扫码明细 |
| 6 | 活动管理页"生成二维码"Dialog 中，若该活动已存在活动类型二维码，是展示已有的还是允许再新建 | 查询已有活动类型二维码展示，不重复创建 | 产品确认：每活动一个活动二维码，还是允许多个 |
