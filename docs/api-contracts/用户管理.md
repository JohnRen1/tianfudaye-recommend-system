## 二、设计原则与审计总纲对应

| 审计问题 | 对应决策 | 契约体现位置 |
|----------|----------|-------------|
| **S1** — 字符串关联蔓延 | `sourceActivityId` / `sourceQrId` 改外键；`userId` 外键贯穿关联实体 | `UserListItemDTO`、`UserTimelineEventDTO`、`UserLeadSummaryDTO` 等 |
| **S2** — 落地页归因链断裂 | 登录请求携带 `sourceQrId` / `sourceActivityId`（落地页读 URL 参数后传入） | `PhoneLoginRequestDTO` |
| **S3** — 写操作不落库 | 登录响应返回 `accessToken`，前端持久化 session | `PhoneLoginResponseDTO`、`WechatLoginResponseDTO` |
| **S4** — 两端枚举不一致 | `RiskLevel` 统一为 4 个英文值；`LeadStatus` 补全 `'none'`（"未生成"）；时间字段全为 ISO 8601 | `shared.ts` 两份副本 |
| **S5** — 认证整体缺失 | 端用户与管理员两套认证路径；管理员三角色枚举；服务端生成字段不出现在写 DTO | `AdminLoginRequestDTO`、`AdminRole`、Create/Update DTO |
| **S6** — 统计值为格式化字符串 | `UserStatisticsDTO` 所有字段为 `number`，不含格式化字符串 | `UserStatisticsDTO` |

## 三、枚举定义

### 3.1 LeadStatus（线索状态）

审计高风险项：原 `LeadStatus` 类型缺少 `'未生成'` 值，`users[4].leadStatus = '未生成'` 导致类型不安全。本契约补全此枚举值。

| 英文值（数据库/API） | 中文展示标签 | 说明 |
|---------------------|-------------|------|
| `none` | 未生成 | 默认状态，尚未生成线索记录 |
| `new` | 新线索 | 刚生成，待处理 |
| `pending` | 待跟进 | 已查看，等待顾问行动 |
| `assigned` | 已分配 | 已分配给顾问 |
| `following` | 跟进中 | 顾问正在跟进 |
| `appointed` | 已预约 | 已预约顾问沟通 |
| `converted` | 已成交 | 转化成功 |
| `invalid` | 无效线索 | 标记无效，不再跟进 |

### 3.2 RiskLevel（风险等级）

审计 S4：原两端枚举不一致（落地页英文 3 值 / 后台中文 4 值）。本契约统一为 4 个英文值，展示层各自映射中文标签。

| 英文值（数据库/API） | 中文展示标签 |
|---------------------|-------------|
| `low` | 低风险 |
| `medium` | 中风险 |
| `high` | 高风险 |
| `critical` | 严重风险 |

### 3.3 AdminRole（管理员角色）

审计 S5：原仅 `username === 'admin'` 二分，本契约引入三角色体系（CLAUDE.md 已规定）。

| 英文值 | 中文展示标签 | 说明 |
|--------|-------------|------|
| `market_ops` | 市场运营 | 活动/二维码/资料管理，查看用户和线索 |
| `tax_advisor` | 税务顾问 | 查看分配给自己的线索和用户详情 |
| `manager` | 管理者 | 全部权限，含系统设置和管理员管理 |

## 六、错误码

### 格式规范

```
{MODULE}_{VERB}_{REASON}
```

所有错误码稳定（不随版本变化），错误 `message` 可本地化。

### 端用户认证错误码

| 错误码 | HTTP 状态 | 说明 |
|--------|----------|------|
| `AUTH_INVALID_PHONE` | 400 | 手机号格式错误（非 11 位纯数字） |
| `AUTH_CODE_NOT_FOUND` | 400 | 验证码不存在（未发送或已过期） |
| `AUTH_CODE_INVALID` | 400 | 验证码错误 |
| `AUTH_CODE_EXPIRED` | 400 | 验证码已过期 |
| `AUTH_CODE_THROTTLED` | 429 | 验证码发送过于频繁（60 秒内重复请求） |
| `AUTH_WECHAT_OAUTH_FAILED` | 502 | 微信 OAuth 授权失败（上游错误） |
| `AUTH_TOKEN_INVALID` | 401 | token 无效或已过期 |
| `AUTH_TOKEN_MISSING` | 401 | 请求缺少 Authorization header |

### 管理员认证错误码

| 错误码 | HTTP 状态 | 说明 |
|--------|----------|------|
| `ADMIN_AUTH_CREDENTIALS_INVALID` | 401 | 用户名或密码错误 |
| `ADMIN_AUTH_ACCOUNT_DISABLED` | 403 | 账号已被禁用 |
| `ADMIN_AUTH_TOKEN_INVALID` | 401 | 管理员 token 无效或已过期 |
| `ADMIN_AUTH_TOKEN_MISSING` | 401 | 请求缺少管理员认证 header |

### 用户管理错误码

| 错误码 | HTTP 状态 | 说明 |
|--------|----------|------|
| `USER_NOT_FOUND` | 404 | 用户不存在 |
| `USER_PHONE_DUPLICATE` | 409 | 手机号已被注册 |
| `USER_PHONE_INVALID` | 400 | 手机号格式错误 |
| `USER_PERMISSION_DENIED` | 403 | 权限不足（如非 manager 尝试创建用户） |
| `USER_TAGS_TOO_MANY` | 400 | 标签数量超出上限（建议上限 20 个） |
| `USER_BULK_IDS_EMPTY` | 400 | 批量操作 userIds 为空数组 |
| `USER_BULK_IDS_TOO_MANY` | 400 | 批量操作 userIds 超出上限（建议上限 100 个） |

### 通用错误码

| 错误码 | HTTP 状态 | 说明 |
|--------|----------|------|
| `VALIDATION_ERROR` | 400 | 请求体字段校验失败，`details` 含具体字段错误 |
| `INTERNAL_SERVER_ERROR` | 500 | 服务器内部错误 |
| `RATE_LIMIT_EXCEEDED` | 429 | 请求频率超限 |

## 七、认证与权限

### 7.1 认证方案

本项目采用两套独立认证体系（审计 S5）：

| 体系 | 使用方 | Token 载体 | 说明 |
|------|--------|-----------|------|
| 端用户认证 | landing-page | `Authorization: Bearer <token>`（推荐 httpOnly cookie） | Supabase Auth JWT，标识端用户身份 |
| 管理员认证 | admin-system | `Authorization: Bearer <token>` | 独立 admin JWT，含 role claim |

**当前阶段（MVP mock）**：两套体系均未接入 Supabase，此契约为下阶段接入的目标设计。

### 7.2 管理员角色权限矩阵

| 接口 | market_ops | tax_advisor | manager |
|------|-----------|-------------|---------|
| 查看用户列表/详情 | 是 | 是 | 是 |
| 查看完整手机号（phoneRaw） | 否 | 是 | 是 |
| 创建用户 | 是 | 否 | 是 |
| 更新用户基本信息 | 是 | 否 | 是 |
| 编辑标签 | 是 | 否 | 是 |
| 批量打标签 | 是 | 否 | 是 |
| 导出用户 | 是 | 否 | 是 |
| 查看用户关联数据（各标签页） | 是 | 是 | 是 |

### 7.3 端用户权限

端用户只能访问自己的数据（`/api/auth/me/*`），不能访问其他用户的信息。

## 八、统一响应格式

所有 API 遵循以下响应包装（详见 `shared.ts`）：

**成功（单条）**：
```json
{
  "success": true,
  "data": { "id": "uuid", "name": "李明", "..." }
}
```

**成功（分页列表）**：

## 九、关键字段约定

### 9.1 phone 字段存储与展示

（对应审计不确定项 #1）

| 位置 | 格式 | 说明 |
|------|------|------|
| 数据库 | 完整 11 位手机号 | 如 `13812345628` |
| 管理后台列表/详情（默认） | 脱敏格式 | `phoneMasked: "138****5628"` |
| 管理后台详情（manager / tax_advisor） | 完整手机号 | `phoneRaw: "13812345628"` |
| 落地页当前用户（自查） | 完整手机号 | `CurrentUserDTO.phone: "13812345628"` |
| 落地页注册提交 | 完整手机号 | `PhoneLoginRequestDTO.phone: "13812345628"` |

### 9.2 时间字段

所有时间字段统一 ISO 8601 字符串格式（S4）：

```
2026-06-04T10:23:00+08:00
```

mock 数据中的 `"2026-06-04 10:23"` 格式在接入真实 API 后必须迁移为 ISO 8601。

### 9.3 id 字段

数据库主键统一使用 UUID 字符串（`string` 类型）。mock 中 `users` 数组使用数字 id（`1`/`2`/`3`）为临时约定，接入 Supabase 后迁移为 UUID。

### 9.4 null 与字段缺失

本契约严格区分：

- `field: null` — 字段存在，值为空（如 `sourceActivityId: null` 表示未绑定来源活动）
- `field?: T` — 字段可能不存在于响应中（如 `phoneRaw` 无权限时不返回该字段，而非返回 null）

### 9.5 sourceActivity / sourceQr 迁移

（对应审计 S1 和修复方案 #3）

| 字段 | 旧格式（mock） | 新格式（API 契约） |
|------|--------------|-----------------|
| `sourceActivity` | 活动名称字符串，如 `"金税四期风险识别专题课"` | 改为 `sourceActivityId`，存活动 UUID |
| `sourceQr` | 混用标识，如 `"ACT-20260702-001"` | 改为 `sourceQrId`，存 `qrCodeItems.id` |

展示时由服务端 join 返回对应的 `sourceActivityName` / `sourceQrName`。

## 十、兼容性与迁移说明

### 10.1 现有页面兼容性

本契约对现有页面的影响分析：

| 页面 | 影响 | 迁移工作量 |
|------|------|----------|
| `admin-system/app/users/page.tsx` | 列表数据源从 mock 改为 API；`sourceActivity` → `sourceActivityName`；时间格式 | 中 |
| `admin-system/app/users/[id]/page.tsx` | 关联数据从全量/name 匹配改为 userId 过滤 API；`sourceActivity` → `sourceActivityName` | 中 |
| `admin-system/app/login/page.tsx` | 硬编码 admin/admin123 改为 `POST /api/admin/auth/login`；localStorage mock-token 改为真实 JWT | 高（安全相关） |
| `admin-system/components/admin-shell.tsx` | token 校验逻辑整体替换；`getUserRole` 改为读取 JWT claim | 高（安全相关） |
| `landing-page/components/mobile/login-register-form.tsx` | 增加真实 API 调用；增加 session 持久化；新增企业信息补录步骤 | 高 |

### 10.2 LeadStatus 枚举迁移

mock 中文值 → API 英文值映射：

| mock 中文值 | API 英文值 |
|------------|-----------|
| `'未生成'` | `'none'` |
| `'新线索'` | `'new'` |
| `'待跟进'` | `'pending'` |
| `'已分配'` | `'assigned'` |
| `'跟进中'` | `'following'` |
| `'已预约'` | `'appointed'` |
| `'已成交'` | `'converted'` |
| `'无效线索'` | `'invalid'` |

前端展示层使用 `LEAD_STATUS_LABEL` 映射中文标签，无需在页面代码中硬编码中文字符串。

### 10.3 RiskLevel 枚举迁移

| mock 中文值（admin-system） | mock 英文值（landing-page） | API 统一英文值 |
|---------------------------|--------------------------|--------------|
| `'低风险'` | — | `'low'` |
| `'中风险'` | `'medium'` | `'medium'` |
| `'高风险'` | `'high'` | `'high'` |
| `'严重风险'` | — | `'critical'` |
| — | `'uncertain'` | **无对应值，需业务确认处理方式** |

注意：落地页存在 `'uncertain'` 值（问答记录模块），admin-system 无对应枚举。此处建议统一为 `'medium'`（中等不确定性），或引入新枚举值，需产品确认。

### 10.4 id 类型迁移

mock 中 `users.id` 为 `number`（1/2/3），API 契约统一为 UUID `string`。

前端需要修改：
- `users/page.tsx` 第 68 行：`row.id` 格式化为 `U0001` 的逻辑改为按 UUID 前 8 位展示或保留原数字序号（产品决策）
- `users/[id]/page.tsx` 第 17 行：`Number(params.id)` 改为直接使用 `params.id`（string）

### 10.5 非 Monorepo 同步约定

本项目无 `packages/` 共享包，以下文件需人工保持同步（双向变更都要同时更新）：

| 后台文件 | 落地页文件 | 同步内容 |
|---------|----------|---------|
| `拓客系统-管理后台/lib/contracts/shared.ts` | `拓客系统-落地页/lib/contracts/shared.ts` | `RiskLevel`、`LeadStatus`、`ApiSuccess`、`ApiFailure`、`PaginatedData` |

建议在 CI 中增加一步校验，提交时检测两份文件的枚举值是否一致。
